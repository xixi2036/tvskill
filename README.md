# TVSkill 上手指南

> 这份文档写给**人**看——不管是刚接手这套流程的同事，还是几个月后忘了细节回来重新捡起的
> 自己。`SKILL.md` 是给 LLM 执行者读的密集规则契约（391 行，假定读者已经理解全部背景），
> 不适合当新手教程；这份 README 补的是"这东西是干什么的、第一次跑起来长什么样、常见的坑
> 在哪"，读完这份再去读 `SKILL.md` 会顺很多。

## 这是什么

把中文竖屏短剧剧本，走完一条完整的 AI 生产链——从剧本文字，到人物/场景/道具/色卡这些视觉
资产，到每个镜头的生成提示词，到最终成片验收——最后交付一份 Markdown，可以同步到 TVMao
画布节点直接生成视频。

**它不是一个"帮你写提示词的模板"，是一台状态机**：九个步骤，每步都有机器闸，跳步在物理上
走不通（不是"不建议跳步"，是命令会直接报错退出）。这个设计不是过度工程——`SKILL.md` 里
记录了真实教训：道具提取、画面覆盖、色卡绑定这三条规则曾经白纸黑字写在文档里，但因为没有
机器闸，一条都没有真的被执行过，而且**没有任何机制发现没落地**，直到成片丢了三成画面才被
人工看出来。台词有对账表所以零丢失，画面当时没有对账表所以丢了三成——差别不在难不难做，
在有没有闸。所以现在这个 skill 的原则是：**能落成闸的规则，一律落成闸；只能靠自觉的规则，
一律假定会被跳过。**

## 目录里都是什么

```
tvskill/
├── README.md              ← 你正在读的这份，人类上手指南
├── SKILL.md                ← LLM 执行契约，规则最全最密的地方，唯一的规则真源
├── scripts/                ← 状态机 + 各类校验器/审计脚本，纯 Python 标准库，不装依赖
│   └── pipeline_state.py   ← 核心：九步状态机，每次开工先问它"该做哪一步"
├── references/              ← 知识库，SKILL.md 的"必读顺序"会点名要求读哪几篇
│   ├── v3/                 ← 导演方法论(镜头/表演/时长切分等)
│   └── libtv/               ← 制作合同(资产生产/画布对接/成片审计等)
├── tests/                   ← 回归测试，改完代码/规则先跑这个
├── assets/                   ← 交付 Markdown 的模板骨架
└── agents/                   ← codex 侧的 skill 元数据
```

一条硬规则：**这个目录必须自包含**。复制整个 `tvskill/` 到另一台电脑，不装任何其它 skill、
不读任何 skill 外部的文件也能跑——所有运行时知识只从 `references/`、`assets/`、`scripts/`
读取。写代码/写文档时如果想引用别处的东西，先想一下这条。

## 第一次跑一集，长什么样

先确认自己在 `tvskill/` 目录下（或用 `--dir` 指定别的目录也行，见下面「常见的坑」）：

```bash
cd <本 skill 所在目录>   # 即这份 README 所在的 tvskill/ 目录，路径因安装位置而异

# 每次开工第一件事：问状态机现在该做哪一步。第一次跑，交付目录要先建好。
mkdir -p /path/to/项目交付目录
python3 scripts/pipeline_state.py status EP01 --dir /path/to/项目交付目录
```

它会打印九个步骤的完成情况，并且明确告诉你"下一步是什么、这一步的闸检查什么、跑闸的命令
长什么样"——**照它说的做，不要自己判断从哪开始**。第一次跑，第一步永远是 `intake`：先把
媒介、单集/全剧范围、资产现状、是否要操作画布、音色状态这几项决策问清楚（怎么问见
`SKILL.md`「开始前」一节，核心方法论是 grilling skill 的"一次只问一题，等回答再问下一题，
能查的事实不问"），写成 `<集号>-任务前置决策.json`，再跑：

```bash
python3 scripts/pipeline_state.py check EP01 intake --dir /path/to/项目交付目录
```

跑通一步，`check` 只验证不改状态；确认没问题后用 `complete` 才真正标记完成并推进状态机。
之后每一步重复"问 status → 做这一步的事 → check/complete"，直到 status 说"全部步骤已完成"。

## 常见的坑（都是实测踩过的，不是猜的）

- **忘传 `--dir`**：早期版本会静默用当前目录，如果你正好在 `tvskill/` 自己的源码目录下跑，
  会在 skill 仓库里生成 `<集号>-run_state.json`，污染 skill 自身且不会有任何提示（这个坑
  已经在 2026-08-01 修掉——现在忘传 `--dir` 会直接报错，不会静默发生，但记录在这里防止
  你在没升级到最新版脚本时踩到）。
- **跳步**：状态机会物理拦截，报错里会写清楚缺哪个前置步骤；不要试图手改
  `<集号>-run_state.json` 绕过去——真要重做某一步，用 `reset` 命令回退，不要手改状态文件。
- **改完交付 Markdown 忘记重跑校验**：`validate` 及其下游步骤会在检测到 Markdown 内容哈希
  变化时自动作废，逼你重跑——这是故意设计的，不是 bug。
- **色卡/资产"看起来生成成功了"就当过关**：`succeeded` 只代表平台任务跑完，不代表结果合格
  （比如色卡可能漏色、错序）。任何涉及视觉资产的步骤都要求"生成后打开实际输出人工核对"，
  节点状态和 prompt 审计都不能替代这一步。
- **拿 ASR 转写当逐字台词真值**：只用本机 `mlx-whisper` 定位复听疑点，不用通用视觉/多模态
  大模型做转写替代品（这类模型在短剧人声上实测会产生幻觉文本，比不转写更危险，因为看起来
  像一份可信的稿子）；专名、数字、短句、情绪必须人工复听。
- **场景语义名漏写前缀**：`@[场景-xxx]`、`@[场景状态-xxx]`、`@[人群状态-xxx]` 这三个前缀
  是校验器判断"这是场景资产还是人物资产"的唯一依据，漏写前缀不会报"这是场景吗"这种直接
  错误，而是被误判成人物资产，在下游触发一串看起来无关的报错（比如"缺身份数量锁"）。

## 这套 craft 规则是从哪来的、多可信

`references/libtv/wanwu-field-craft.md` 和 `SKILL.md` 里大量规则的来源是「万物生」——一个
在 Neowow 无限画布上真实上线的爆款短片项目（正传 + 姊妹篇《问心》），逆向蒸馏出的手法。
这不是凭空定的规矩，是从真实跑通的产线倒推出来的。

2026-08-01 做过一轮系统性重新比对（正传近期 bug 清单落地状态 + 问心新增手法 vs 当前
contract），结论：

- 历史 bug 清单（六件套结构、音色占位、画面/语音双对账、九步状态机跳步拦截等 20+ 项）
  绝大多数已经在代码/文档层面落地，只剩三处收尾细节（ASR 工具指名、场景前缀显式规范、
  内联音频特殊路径）当时是缺口，现已补齐；
- 问心相对正传的新增手法（22/24 色卡扩展档、去字幕+扩图后期节点、排除式定义、Reference
  身份/姿态分离绑定）当时有 3 条完全没吸收、1 条只有零散原则没有具体写法，现已补齐。

这轮比对的完整过程记录在独立知识库项目里（不在本 skill 目录内，按"独立迁移合同"skill
自身不该依赖外部路径，故只在此处提一句方向，不写死具体路径）。**下一次再做类似比对时**，
建议先看 `SKILL.md` 和 `references/` 里最近改动的 git log，再去核对知识库里是否有更新的
手法还没吸收进来——不用每次都从头通读全部历史文档。

## 改完代码/规则，怎么验证没搞坏

```bash
cd <本 skill 所在目录>
python3 -m unittest discover -s tests -p "test_*.py"
```

纯标准库 `unittest`，不需要装 `pytest`。改动涉及某个具体校验器时，先看 `tests/` 下有没有
同名测试文件，大概率有——这个 skill 的原则是"能落成闸的规则一律落成闸"，配套的原则是
"落成闸的东西一律配回归测试"，改动如果让某条已有测试失败，先想清楚是测试该更新（你在做的
是一次深思熟虑的契约扩展）还是代码改错了，不要为了让测试通过就删掉断言。

## 版本控制

`tvskill/` 目前是一个独立的 git 仓库（2026-08-01 建，此前没有版本控制）。`.gitignore` 排除
的是运行期产物（`*-run_state.json`、`*-画面单元.json`、`__pycache__/` 等）——这些是具体
出片项目的交付目录里才会出现的文件，不该跟着 skill 源码一起提交；如果你在 `tvskill/`
目录本身看到这类文件，大概率是忘传 `--dir` 生成的，删掉即可，不影响 skill 本体。
