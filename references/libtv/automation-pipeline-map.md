## 2. 结构性诊断：有状态机，没有执行器

`pipeline_state.py` 的命令只有 `status / check / complete / reset`——
它**记录**某步做完了，从不**执行**那步。真实执行路径是：

```
人/LLM 读 SKILL.md → 自己决定调哪个脚本 → 手动调 → 回头告诉账本「complete」
```

对比巨日禄：ForceAsync 后台 worker、30s 轮询收敛、tasks.json 台账断点续查、防重提。
**那边是流转，这边是自觉。** 跳步在这条路径上零阻力，所以必然反复发生。

### 失衡量化

九步中前 7 步（script_units→review）全部对应巨日禄的 ⓪ 一个节点；
巨日禄的 11 个下游执行节点（①–⑪）被压进最后 2 步：

- `canvas` gate：sync dry-run 与画布只读审计零硬错误
- `generate` gate：需用户逐节点授权；成片十轴审计通过

**七步精雕提示词，十一个执行节点两步带过。**
2026-09-04 的四次跳步全部落在这两步内——这是结构决定的，不是注意力问题。

## 3. 待裁决的真实冲突：⑨候选池 vs 一次性视频预算

两条规则当前直接对撞：

- 巨日禄 ⑨：`MaterialCandidate·AddCandidate` 重生成/多候选择优——**承认一次跑不出好镜头**
- tvskill 现行：`audit_canvas_nodes.py:523` 一次性视频预算，`runCount≥1` 即硬拒，failed 节点永久拒绝态

一次性预算是省积分的闸，但它同时**取消了择优能力**。
若目标是复刻《万妖图录传》那一档成片质量，需要明确：

- 保留一次性预算 → 接受"一镜一次定生死"，质量上限受单次抽卡运气限制
- 引入候选池 → 需要给出每镜候选上限与择优判据，预算闸改为按候选数计

**此项未决，不得由实现方私自选边。**

## 4. 补齐优先级（按对产线的阻断性排序）

1. **③ 合规校验封装**（P0）——缺它则真人/写实素材的视频生成必失败且烧积分。
   画布侧命令已存在，只是没有工具把它锁进流程。
2. **⑧ 本地台账**（P0）——无台账则断点续查、防重提都做不到，
   同时 `runCount` 只能现读画布，离线不可判。
3. **下游步骤纳入状态机**（P1）——把 ①–⑧ 从 `canvas`/`generate` 两步里拆出来，
   每个节点有独立 gate，跳步才会被账本拒绝。
4. ⑨/⑩/⑪ ——待 §3 裁决后再定。
